# Traefik & DockFlare: operations guide

Private routing (`*.lan.example.com`) uses Traefik with Docker labels, the same pattern as DockFlare (`exposedByDefault: false`: only containers with `traefik.enable: "true"` are exposed). There is no central, hand-maintained routes file.

**Public certificate via Let's Encrypt (DNS-01/Cloudflare)**: resolver `cloudflare` (Lego, `CLOUDFLARE_DNS_API_TOKEN=${CF_API_TOKEN}`, reusing DockFlare's token, which has `Zone:DNS:Edit` on the `example.com` zone). The DNS-01 challenge creates and deletes a temporary `_acme-challenge` TXT record through the Cloudflare API, so no port 80/443 is exposed to the internet and there is no public A record. Split-horizon DNS still keeps access LAN/VPN-only: Pi-hole is the only resolver that maps `*.lan.example.com` to the internal IP, and Traefik is never exposed through the tunnel/DockFlare. The certificate is a **single wildcard** (`*.lan.example.com`, declared via `tls.domains` on the `traefik-dashboard` router). Every other router only sets `tls.certresolver: cloudflare` and reuses the same cert from the store (SNI match): no repeated `tls.domains`, no per-service ACME request. Unlike the internal CA (step-ca) it replaced, the certificate is trusted natively by any OS/browser, so no root CA has to be installed on each new device.

**`acme.json`/`acme-cloudflare.json` must exist with `chmod 600` before the first start.** Traefik refuses to start if permissions are looser (`scripts/setup/setup-traefik-config.sh` handles this).

Per-service label pattern (zangetsu, same Docker network as Traefik):
```yaml
labels:
  traefik.enable: "true"
  traefik.http.routers.<nome>.rule: "Host(`<nome>.lan.example.com`)"
  traefik.http.routers.<nome>.entrypoints: "websecure"
  traefik.http.routers.<nome>.tls.certresolver: "cloudflare"
  traefik.http.routers.<nome>.middlewares: "crowdsec@file"
  traefik.http.services.<nome>.loadbalancer.server.port: "<porta>"
```
**CrowdSec does not apply to every route automatically.** The Traefik plugin (`maxlerebourg/crowdsec-bouncer-traefik-plugin`) requires the `crowdsec@file` middleware to be referenced on **each** router. Confirmed: Traefik has no native "apply to every router" option at the entrypoint level (unlike the old Caddy plugin, which covered everything).

**Private service running outside zangetsu (e.g. urahara) or on an external host (Headroom, QNAP)**: Traefik only discovers containers through the Docker provider of the host it runs on. Instead of labels, use the file provider: `infra/platform/networking/traefik/config/dynamic/cross-host.yml`, one `router` + `service` per entry, pointing at IP:port. zangetsu still publishes no ports for this (documented exception: `dockflare` publishes 5000 so the remote DockFlare Agent can reach the master).

`pihole.lan.example.com` (redirect `/` → `/admin/`) and the `headroom.lan.example.com` redirect use the `redirectRegex` middleware.

**Traefik dashboard**: `traefik.lan.example.com` points at the internal `api@internal` service. Internal access for widgets (Homepage) goes through port 8080, which is not published (`api.insecure: true`): reachable only inside the Docker network, never on the host.

**Real quirk: the DockFlare master needs `USE_EXTERNAL_CLOUDFLARED=true`.** Without it, DockFlare runs in "managed" mode (the default) and treats the `cloudflared-agent-lemonpi-5-tunel` container as its own: it manages the container lifecycle directly through the Docker API (outside `docker compose`), without the `com.docker.compose.*` labels. `CLOUDFLARED_IMAGE` (the officially documented variable for managed mode) **does not fix it**: tested, DockFlare ignores the value even when `docker exec printenv` confirms it inside the container, and keeps treating `latest` as the desired image. Whenever DockFlare detects a "mismatch" (our pinned tag in `cloudflared-agent.yaml` vs. what it wants), it recreates the container itself, and any later `docker compose up`/`--force-recreate` collides on the name (`Conflict: container name already in use`) because Compose does not recognize the container as its own. Fix: `USE_EXTERNAL_CLOUDFLARED=true` + `EXTERNAL_TUNNEL_ID=${CF_TUNNEL_ID}` in `dockflare.yaml`. This switches to external mode, where DockFlare only reads labels for ingress/DNS and never touches the container lifecycle ([official docs](https://github.com/ChrispyBacon-dev/DockFlare/wiki/ExternalcloudflaredMode.md)). `CF_TUNNEL_ID` is the tunnel UUID, taken from the `CF_TUNNEL_TOKEN` payload itself: the token is base64 of `{"a":account_id,"t":tunnel_id,"s":secret}`, so decode it and take `"t"`. Nothing new needs to be generated or looked up. Validated with a full stack recreate (`docker compose up -d --force-recreate`, unscoped) twice in a row: exit code 0, no conflict.

**`dockflare-init`/`dockflare-agent-init` (chown `/opt/apps/dockflare*` to UID 65532) use `profiles: [init]`, with no `depends_on` from the main service.** This is deliberate. The alternative (`depends_on: service_completed_successfully`) leaves the container in `Exited(0)` forever after every `docker compose up -d`, cluttering the Komodo listing with no way to hide it. Komodo has no native label to hide an individual container from the UI; `komodo.skip` only affects the bulk "Stop All Containers" action (confirmed; not what the name suggests). Accepted trade-off: with `profiles: [init]`, the container **no longer runs automatically**. On a new host, or after resetting the `/opt/apps/dockflare`/`/opt/apps/dockflare-agent` volume, run it manually **before** the main service's first `docker compose up -d`: `docker compose --profile init up -d dockflare-init` (zangetsu) or `docker compose --profile init up -d dockflare-agent-init` (urahara). Otherwise `dockflare`/`dockflare-agent` fails on permissions at first start (they run as UID 65532 and cannot write to a directory just created as root).

**Host-agnostic fragment that needs a port on only one host** (included on more than one host): do not add `ports:` directly to the fragment in `infra/`. That would break the host that should not publish anything, or worse, point at a LAN IP that does not exist on that host. Create a small override file in `hosts/<hostname>/`, included *after* the original fragment in `include:`, containing only that host's `ports:` (see `hosts/urahara/observability-ports.yaml`). If two hosts run the same host-agnostic service and both need their own `*.lan.example.com` hostname (same container/`container_name` on both, so the hostname cannot be reused), suffix the hostname of the non-zangetsu host (e.g. `<service>-urahara.lan.example.com`).

**An `include:` override file does not merge nested fields inside `networks:`.** `ports:`/`environment:` (lists) merge correctly between base fragment and override (tested, works), but `networks: <network>: ipv4_address:` (a map nested in a map) **does not merge**: the base fragment's value always wins, even with the override listed later in `include:` (real bug, found the hard way with `pi-hole` on urahara). For a static IP that must vary per host, do not use a file override for that field. Use `${VAR:-default}` in the base fragment and set the variable only in the `.env` of the host that needs a different value (see `PIHOLE_STATIC_IP` in `pi-hole.yaml`/`hosts/urahara/.env`).
