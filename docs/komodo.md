# Komodo (multi-host Docker management)

Core runs only on zangetsu (`infra/platform/management/komodo/komodo.yaml`: postgres + ferretdb + core). Periphery is host-agnostic, one agent per host (`infra/platform/management/komodo/periphery.yaml`). Automatic deploy via GitHub Actions (`.github/workflows/deploy.yaml`) calls the `/listener/github/stack/<id>/deploy` webhook per host, filtering by the `include:` of each `hosts/<host>/compose.yaml`, so only the host(s) affected by the push diff are deployed.

**Critical rule, learned in production: `komodo-core` and `komodo-periphery` must NEVER be in the `include:` of the `compose.yaml` that the `homelab-<host>` Stack itself manages in Komodo.** Reason: a real `DeployStack`/`DeployStackIfChanged` that recreates the Core or Periphery container (because it belongs to the stack being deployed) kills the very process running the deploy. Periphery runs `docker compose` as a subprocess inside itself, and Core tracks deploy progress inside itself. Observed symptom: half the host's containers stuck in `Created` (they never reach `Started`; `restart: unless-stopped` does not help because the container never existed to have a restart policy applied), and the Stack stuck in `DOWN`/`0 Services` (the update stays "Complete"/`success:false` forever, with log `"Komodo shutdown during execution"`, or the Periphery process simply disappears).

**Removing them from `include:` is not enough** (tested and confirmed). Even outside the main `compose.yaml`'s `include:`, the container still carried the Stack's `com.docker.compose.project` (`homelab`, inherited from the `project_name:` set on the Stack), and Komodo operates at the **Compose project** level, not only on the declared files/services. Fix: `hosts/<host>/komodo-periphery.yaml` and `hosts/zangetsu/komodo-core.yaml` are **separate Compose projects** (`name: komodo-periphery` / `name: komodo-core`, `networks: cloudflare-net: external: true`, `include:` of only the relevant fragment(s), never of the main `compose.yaml`, which would drag in the whole `homelab` project). Deploying/updating these two is **always manual**, never via Komodo/webhook:
```bash
cd hosts/<host> && docker compose -f komodo-periphery.yaml up -d
cd hosts/zangetsu && docker compose -f komodo-core.yaml up -d   # zangetsu only; Core does not run on urahara
```
On urahara, `komodo-periphery.yaml` includes an extra override (published port). It is a separate host-specific file (`komodo-periphery-port.yaml`), not to be confused with the host's main `compose.yaml`.

Consequence: `komodo-core` can no longer have `depends_on: dockflare` (cross-project dependencies do not work in Compose), so it was removed from `komodo.yaml`. `dockflare` is already up persistently before Core actually needs it.

**Known bug (Komodo v2.3.2), STILL PRESENT in 2.3.3: do not use `DeployStackIfChanged`.** It hangs forever (no error, no log, no persisted update) on a Stack whose `compose.yaml` is `include:`-heavy, confirmed both via webhook and via a direct `/execute` API call. `RefreshStackCache` alone works fine in 2.3.3 (clone/diff OK), but `DeployStackIfChanged` specifically still hangs. The hang is intermittent enough to be misleading: in a real test with an actual `mem_limit` diff, it worked 2 out of 3 times before hanging on the third. **Always set `webhook_force_deploy: true` on both Stacks.** Do not revisit this without first reproducing a controlled test (real diff, not just `RefreshStackCache`) several times in a row. Keep Core and Periphery on the same version (`docker compose pull <service> && docker compose up -d --force-recreate <service>`; `--force-recreate` alone does **not** pull a new image, so always `pull` first).

**Webhook secret**: if the Stack's `webhook_secret` field is empty, it falls back to Core's global `KOMODO_WEBHOOK_SECRET` (no per-Stack override is needed unless you want a dedicated secret, as `homelab-urahara` has). The GitHub Actions secret (`KOMODO_HOMELAB_<HOST>_WEBHOOK_SECRET`) must exactly match what the Stack actually uses (the global one if it has no override). A mismatch makes `curl -f` fail with exit 22 (HTTP 4xx) in the Actions job, silently until someone checks the run.

**`git` "dubious ownership"**: a Stack in native git-clone mode (`clone_path=/opt/homelab`, writing directly to the real repo path) needs `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_N`/`GIT_CONFIG_VALUE_N=safe.directory` in Periphery's `environment:` (equivalent to `git config --global --add safe.directory`, without depending on a persisted `.gitconfig`). Without it, `git remote set-url`/clone fails with "detected dubious ownership" because the owner of `/opt/homelab` on the host (user `admin`) differs from the user running Periphery (root, inside the container).
