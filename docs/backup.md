# Backup: databases and multi-host Restic

## Database backup
Rule: every database used by a service (SQLite, Postgres, etc.) needs a consistent snapshot from a script run by Dagu, following the `sqlite-backup.yaml`/`postgres-backup.yaml` pattern. Never rely on Restic's hot copy: a database in use can be corrupted if copied directly.

- SQLite: `scripts/backup/backup-sqlite.sh`, DAG `sqlite-backup` (02:30, zangetsu). Uses SQLite's own `.backup`, writes to `<app>/db-backup/`, keeps the 7 most recent. **Exception: n8n (urahara)**. It is the first SQLite service outside zangetsu, and a local `docker.run` cannot reach the file. It uses `scripts/backup/backup-n8n-sqlite.sh` + `scripts/backup/rename-n8n-workflow-backups.sh`, DAG `n8n-backup-urahara` (02:35, `action: ssh.run` on urahara, same pattern and `\$` escaping + `shell: /bin/sh` quirk as `restic-backup-urahara`), and pings Healthchecks via the published IP:port (`192.168.10.214:8000`) instead of the container name.
- Postgres: `scripts/backup/backup-postgres.sh`, DAG `postgres-backup` (02:35, zangetsu). Runs `pg_dump` per database (reaches `paperless-db`/`immich-db` on urahara over the network via IP:port; it does not need to run next to them). The DAG runs in a `postgres:17-alpine` runner container, which **must always be the same version as or newer than the newest Postgres in the stack**: `pg_dump` refuses to dump a server newer than the client (`aborting because server version mismatch`), but reads older servers fine. Confirmed in production: `komodo-postgres` (FerretDB's backend) runs Postgres 17, and a runner still on `postgres:16-alpine` broke the whole DAG, retrying for hours. When adding a service whose Postgres major version is newer than the current runner, bump the runner tag first.
- New service with its own database: add it to the matching script (do not create a new DAG). There is **no** need to touch `scripts/backup/restic-excludes.txt`: its patterns are generic (any `.sqlite`/`.sqlite3`/`.db` + `-wal`/`-shm` sidecars directly under `/opt/apps/<app>/`, and any `/opt/apps/<app>/db/`), so they cover new services automatically. Edit it only if the new database falls outside both patterns (non-standard file name, or a Postgres data dir not named `db/`).

Practical consequence: **do not version n8n workflow JSON exports in the repo.** n8n's `database.sqlite` (workflows + credentials + executions) is already covered by the backup above; keeping JSON alongside it is redundant and goes stale.

## Multi-host Restic
Filesystem backup (`/opt` + `/etc`) with **Restic**, run as a throwaway container triggered by Dagu (`action: docker.run`, same pattern as `sqlite-backup.yaml`/`postgres-backup.yaml`). It is not a persistent app, and the whole config (DAG + script + exclude file) lives in git rather than in a web UI.

- **Repository**: local path on a fixed CIFS mount from the NAS: `nas-drive/backup/servers/<host>/restic` → `/mnt/backup/<host>`, same fixed `.mount` pattern as the media mounts (never `.automount`). `backup/` is a folder inside the `nas-drive` share (`admin` only, no OneDrive sync), and `servers/<host>/` keeps the homelab host backups apart from other things in `backup/`. No remote storage credentials: from Restic's point of view it is a local filesystem, so only `RESTIC_PASSWORD` (repo encryption) is needed in each host's `.env`.
- **DAGs, zangetsu** (`infra/automation/dagu/dags/`): `restic-backup-zangetsu` (02:40, after `sqlite-backup`/`postgres-backup`) and `restic-prune-zangetsu` (Sunday 04:00, `restic forget --prune` with GFS retention: 7 daily / 4 weekly / 6 monthly).
- **DAGs, urahara**: run on the **same Dagu instance (zangetsu)**, but with `action: ssh.run` instead of `docker.run`. The step connects to urahara over SSH and runs `docker run` there (`restic-backup-urahara` 02:45, `restic-prune-urahara` 04:30). Why not `docker.run`: Dagu cannot target a remote Docker daemon per *step*, only per process (`DOCKER_HOST` in the environment of the whole `dagu` container), which would affect zangetsu's local DAGs (confirmed in the official Dagu docs before implementing, not assumed). `ssh.run` avoids this without a second Dagu instance.
  - Dedicated SSH key (`dagu-restic-urahara`, ed25519), generated outside the repo. It lives in `/opt/apps/dagu/ssh/` on zangetsu (bind-mounted `:ro` into the `dagu` container at `/opt/homelab-ssh`, never committed to git) and is authorized in the `authorized_keys` of user `admin` on urahara.
  - The remote `docker run` uses `--network cloudflare-net` (**urahara's** network: same name, different subnet from zangetsu's) and pings Healthchecks via IP:port (`192.168.10.214:8000`, published specifically for this in `healthchecks.yaml`) instead of the `healthchecks` container name, since it is not on zangetsu's Docker network and name resolution does not work. The IP must also be in Healthchecks' `ALLOWED_HOSTS` (Django rejects any Host header not in the list with a 400). This was a real production error (`HTTP/1.1 400 Bad Request`) until `192.168.10.214` was added to the env var.
  - **Real quirk, took time to find**: `action: ssh.run` runs `command:` through a real remote shell (SSH exec). This differs from local `action: docker.run`, which sends the command straight to the Docker API via the SDK, with no shell in between. It matters because `command:` here is `docker run ... sh -c "script with \$variable and \$(subshell)"`. Without escaping `\$`, the **outer remote shell** (the one doing the SSH exec) evaluates `$envf`/`$(...)` first, before the container even exists, so the variable ends up empty (`RESTIC_PASSWORD=` empty; real production error: `Fatal: an empty password is not allowed`). You must escape with `\$` **and** set `shell: /bin/sh` explicitly in the step's `with:`. Without an explicit `shell:`, Dagu itself strips the `\` before sending over SSH (documented behavior: "without `shell` configured, Dagu unescapes before sending"), reproducing the same bug. Tested and confirmed with a throwaway DAG before applying to the real DAGs.
- **Exclude file**: `scripts/backup/restic-excludes.txt`, non-recursive patterns (`/opt/apps/*/*.sqlite` etc., not `/opt/apps/**/*.sqlite`). They match only files directly in the app folder, never inside `db-backup/` (one level deeper), so the SQLite/Postgres backups themselves are never excluded by mistake.
- **Restore**: one-off container with the same repo mount (`/mnt/backup/<host>:/repo`), `restic restore latest --target <destination>` (or `restic snapshots` to pick a specific point).
- Each host with data to protect needs its own mount + pair of DAGs (backup + prune). Never use a central repository covering both hosts.
